# Password Reset (PR-09)

Secure password recovery for customers and administrators. A locked-out
customer or admin can recover access without support intervention.

## Flow

1. The user opens **/forgot-password** (linked from the login page as
   "Forgot password?") and submits their email address.
2. `POST /api/auth/forgot-password` rate-limits the request and enqueues
   exactly one outbox row carrying only the submitted normalized email
   address — the same row for every valid email — then returns the same
   200 immediately. The response is identical whether or not an account
   exists, so the endpoint cannot be used to probe which emails are
   registered (enumeration-safe).
3. A background worker (`src/services/email-outbox.service.ts`, started
   from `src/instrumentation.ts` on a 60-second sweep) picks up the row
   and performs the account lookup AFTER the HTTP request has returned.
   For a credentials account it generates a single-use token, stores only
   its hash, and sends the reset link (`/reset-password?token=...`) by
   email. For an unknown or OAuth-only address it silently discards the
   row without sending anything.
4. The user opens the link and submits a new password (min 8, max 72 chars,
   same `passwordSchema` as registration) to `POST /api/auth/reset-password`.
5. The token is redeemed atomically: it is marked consumed only if still
   unused and unexpired, and the password is changed in the same
   transaction. The token can never be reused.
6. The user signs in with the new password. The old password stops working
   immediately.

## Why the email is sent asynchronously (security-review fix)

Sending the reset email synchronously from the forgot-password endpoint
leaked account existence in two ways, even though the response text was
identical:

- **Timing**: a registered account triggered a DB write plus an SMTP
  round-trip (hundreds of milliseconds to seconds), while an unknown
  address returned in a few milliseconds. An attacker measuring response
  times could distinguish them.
- **SMTP failures**: when SMTP was down or unconfigured, a registered
  account surfaced a 503 while an unknown address got a 200 — the status
  alone revealed the account exists.

The outbox removes both leaks structurally: the endpoint never sends
email and never checks SMTP configuration. It does the same single DB
write and returns the same 200 for every address. SMTP failures happen
in the background worker, are retried with exponential backoff (30s, 1m,
2m, 4m, 8m, up to 5 attempts), and never reach the HTTP response. After
5 failed attempts the row is marked FAILED and an error is captured for
operators; it is never retried automatically.

A second, subtler leak was also closed: the request path used to call
`findUserByEmail()` before enqueueing, so the HTTP request still performed
account-dependent database work (the lookup returned different results for
registered and unknown addresses, and the outbox row stored different
userId values). The request path now performs **no account lookup at all**
— it enqueues only the submitted normalized email address, the same row
for every valid email. The worker performs the account lookup after the
HTTP request has returned, and silently discards unknown and OAuth-only
addresses. The outbox row carries no userId, no name, and no lookup
result, so the row itself cannot encode whether an account exists.

Trade-off: if SMTP is not configured or is down, users who request a
reset get the "a reset link has been sent" message but no email arrives.
That is the necessary cost of enumeration safety — the endpoint cannot
say the email failed without revealing whether an account exists.
Operators must ensure SMTP is configured and monitor the outbox for
FAILED rows (they are captured via the error-monitoring alert path).

## Token design

Mirrors the email-verification token pattern
(`src/services/email-verification.service.ts`):

- Token: 32 cryptographically secure random bytes (`randomBytes(32)`),
  base64url-encoded.
- Only the **SHA-256 hash** is stored (`PasswordResetToken.tokenHash`,
  unique). The raw token is emailed once and never persisted or logged.
- **The token is generated by the outbox worker at delivery time, not by
  the endpoint.** The outbox row carries only the submitted email address
  — no userId, no name, no lookup result — so the raw token is never
  written to the outbox and the row cannot encode whether an account
  exists. The worker looks the account up, generates the token, stores
  only its hash, and sends the raw token in the email. The token only
  ever exists in the worker's memory and in the email itself.
- **TTL: 1 hour** (`PASSWORD_RESET_TOKEN_TTL_MS`), starting when the worker
  creates the token (i.e. when the email is sent, up to ~60s after the
  request).
- **Single-use**: `consumedAt` is set atomically with an
  `updateMany({ where: { id, consumedAt: null, expiresAt: { gt: now } } })`
  guard, so concurrent redemptions only succeed once.
- **Separate table** from `VerificationToken`, so a verification token can
  never be redeemed as a reset token (and vice versa). Verified by an
  integration test.
- Issuing a new token deletes all previous reset tokens for that user, so
  only one valid token exists at a time. (The worker does this at delivery:
  if two reset requests are enqueued before the worker runs, the second
  delivery replaces the first token.)
- Only credentials accounts (`passwordHash` set) receive a token. OAuth-only
  accounts have no password to reset and their outbox rows are discarded
  by the worker, silently. Unknown addresses are discarded the same way.

## Session invalidation (the JWT design decision)

NextAuth v4 uses JWT sessions, and **JWTs are not revocable**. A password
reset therefore cannot invalidate existing sessions by deleting a server-side
record — there is none. Instead, a successful reset records
`User.passwordChangedAt`, and the auth guard (`src/lib/auth-guard.ts`)
rejects any session whose JWT was issued at or before that timestamp:

- `auth.ts` exposes the JWT issued-at time on the session (`session.iat`).
- The guard already re-fetches the user from the DB on every protected
  request (to re-verify the role), so the check adds no extra query: it
  reads `passwordChangedAt` from that same fetch and returns `null`
  (unauthenticated) when `passwordChangedAt >= iat`.
- The user must then sign in again with the new password. Sessions issued
  after the reset are unaffected.
- A session whose token carries no issued-at time (pre-PR-09) cannot be
  compared and stays valid until its own 7-day expiry; this only affects
  tokens issued before this change deployed.

**The `iat` must be the original issuance time (PR-25).** NextAuth v4's
default `jwt.encode` stamped a fresh `iat`/`exp` on every encode, so
`GET /api/auth/session` re-issued a token with fresh timestamps and a
password reset could not kill it (the re-encoded `iat` landed after
`passwordChangedAt`). `auth.ts` now wires a custom encoder
(`src/lib/session-token.ts`, Node built-in `crypto` only, no new
dependency) that preserves the original `iat`/`exp` when re-encoding an
existing token and stamps fresh values only at sign-in. A session can
therefore never be extended past its original expiry, and the invalidation
check above holds for refreshed tokens too. The same preserved `iat` is
what the admin MFA guard compares `lastVerifiedAt` against.

**`passwordChangedAt` is stamped after the password hash (PR-25, E-2).**
The timestamp used to be captured before `bcrypt.hash` ran, so a session
issued while bcrypt was running — before the password actually changed —
survived the reset. It is now captured immediately after the hash
completes, inside the same transaction.

## Rate limiting

- `POST /api/auth/forgot-password`: 10 requests / 15 min per IP, plus
  3 requests / hour per email address (SHA-256 hash of the email is the
  key, so the raw email is not stored in the limiter).
- `POST /api/auth/reset-password`: 10 attempts / 15 min per IP, to slow
  token guessing. Tokens are 32 random bytes, so guessing is infeasible;
  the limit is defence in depth.
- Limits are per-instance in-memory (same as the rest of the app's rate
  limiting; see PR-11 for the shared-store follow-up). A 429 response
  includes `retryAfterSec`.

## Email

`sendPasswordResetEmail` (in `src/services/email.service.ts`) mirrors
`sendVerificationEmail`: same SMTP configuration and pooled transporter,
HTML + plain-text bodies, 1-hour expiry stated in the message, and a note
that ignoring the email leaves the password unchanged. It is called only
by the outbox worker, never by the forgot-password endpoint. If SMTP is
not configured, the worker's sends fail, retry with backoff, and are
eventually marked FAILED — the endpoint still returns 200 (see "Why the
email is sent asynchronously" above).

## The outbox worker

`src/services/email-outbox.service.ts` exports `enqueuePasswordResetEmail`
and `enqueueVerificationEmail` (single INSERTs carrying only the email, deduped
against an existing PENDING row for the same type and email),
`deliverPendingOutboxEmails(batch)` (one sweep; exported so tests and
operators can invoke delivery directly), `listEmailOutboxEntries` /
`getEmailOutboxEntry` / `retryEmailOutboxEntry` (the admin viewer and retry),
`cleanupEmailOutboxEntries` (retention), and `startEmailOutboxWorker()`
(in-process 60-second sweep, single-flight, unref'd timer, started from
`src/instrumentation.ts` alongside the payment maintenance worker). Rows are
claimed atomically (conditional update on status + nextAttemptAt) so two
instances racing on the same row cannot both deliver it. The worker never
logs tokens, email bodies, or customer data — only the outbox row id and the
error name.

The outbox carries two email types. `PASSWORD_RESET` rows are created by the
forgot-password endpoint; `EMAIL_VERIFICATION` rows are created by
registration and by the resend-verification endpoint (Phase 3 Chunk 7,
M-24). Both are delivered by the same worker with the same retries: the
worker looks the account up at delivery time, generates the token then,
stores only its hash, and sends the email. Unknown, OAuth-only, and (for
verification) already-verified addresses are silently discarded. One
deliberate limitation: a row carries only type + email — there is no payload
column — so a verification email delivered from the outbox cannot carry the
request's callbackUrl, and its link uses the default "/account" destination
instead. The token itself is generated identically (32 random bytes,
base64url, SHA-256 hash stored, 24h TTL).

## Admin visibility, retry, retention

A FAILED row is terminal — the worker never retries it automatically — and
used to be visible only in error monitoring. The admin outbox viewer
(`/admin/email-outbox`, sidebar: "Email outbox") lists every PENDING and
FAILED row with its type, recipient, attempts, last error and age, with a
status filter and a detail view per row. A FAILED row can be retried from
the detail view (`POST /api/admin/email-outbox/[id]/retry`, audited as
`admin.email.outbox_retried`): the retry is a conditional update that only
succeeds while the row is still FAILED, resetting it to PENDING with a fresh
attempt budget. Delivered and discarded rows are deleted by the worker, so
they never appear here.

Retention: FAILED rows older than 30 days are deleted by
`cleanupEmailOutboxEntries()`, wired into the shared maintenance runner as
the `cleanup_email_outbox` action — it runs in the payment maintenance
worker's sweep and can be triggered manually via `POST
/api/admin/payments/maintenance`. PENDING rows are never deleted. No
retention convention existed anywhere in the codebase, so 30 days is the
documented choice: long enough to investigate a delivery failure, short
enough that the table stays small.

## Worker configuration

Each in-process worker has its **own** opt-out environment variable, and
they are independent — disabling one must never silently disable the other:

- `PAYMENT_MAINTENANCE_WORKER=off` disables only the payment maintenance
  worker. It does **not** disable the email outbox worker. (This was a
  real bug in the first version of this PR: the instrumentation hook
  returned early on this setting, which silently stopped password-reset
  delivery too.)
- `EMAIL_OUTBOX_WORKER=off` disables only the email outbox worker. It does
  **not** disable the payment maintenance worker.
- With neither set, both workers start in the normal Node.js server
  runtime. Neither worker starts outside the Node.js runtime (e.g. Edge)
  or during the production build phase.

**Serverless deploys:** the in-process workers do not run there. Set the
corresponding opt-out (`EMAIL_OUTBOX_WORKER=off` for the email worker,
`PAYMENT_MAINTENANCE_WORKER=off` for the payment worker) and use an
external scheduler to invoke delivery instead: call
`POST /api/admin/email-outbox/deliver` for outbox emails (admin
MFA-verified session required; same delivery as the worker, safe to call
concurrently with it) and `POST /api/admin/payments/maintenance` for
payment maintenance. If the email worker is disabled and no scheduler is
configured, enqueued reset emails simply wait in the outbox — they are not
lost, but they are not delivered until a sweep runs.

## What is NOT covered

- Password reset does not verify the email address: an account that never
  verified its email still cannot sign in with a password (the credentials
  provider requires `emailVerified`). Resetting the password for such an
  account is harmless — the reset email itself proves ownership of the
  address — but the user must still verify their email to sign in.
- There is no "change password while signed in" flow yet; that is a
  separate feature (the reset flow covers the locked-out case).
